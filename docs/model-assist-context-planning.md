# 模型辅助的上下文规划

状态：设计提案，尚未修改运行时实现。适用于找证据、提议切片和固定截止点起草要求。

## 1. 决策

采用“完整原文保留 + 按实际模型预算规划请求”的方案：

1. 取消每条消息只发送前 4000 字符的规则。允许拆分，但不能丢掉剩余内容。
2. 能装下所选分析范围时直接发送，不做相关性预筛选或摘要替换。
3. 装不下时，按会话结构划分分析窗口，逐窗口扫描；摘要和索引只用于导航，候选精查必须取回有出处的原文。
4. 同模型不直接等于能发送完整历史。路由依据是“这次实际发送的内容是否能装下”，不是模型名字是否相同。
5. 候选发现可以看后续历史；编写要求和 rubric 时重新构造截止点之前的有效上下文，禁止把后续事实当作当时要求。
6. 无法在目标模型窗口内组成充分证据时，返回“上下文不足”，不能伪装为“没有候选”。

不能保证模型不漏判，也不能声称摘要不丢语义。能保证的是：不静默丢弃原文；明确哪些原文发送过、哪些只被摘要表示、哪些尚未处理；最终引用可回到来源核验。

## 2. 首先区分两个来源视图

| 视图 | 内容 | 用途 |
| --- | --- | --- |
| 当前有效上下文 | 宿主在当前分支叶子处恢复的摘要、保留消息、有效的历史指令及可恢复的上下文编辑结果 | 理解当前问题、分析当前仍可见的内容 |
| 分支历史档案 | 所选分支从根到叶子的记录，包括已被压缩或 reset 移出当前上下文的消息 | 寻找历史错误、恢复每个候选当时的可见上下文 |

“用户目前的对话能装下”通常说的是第一行，不是第二行。压缩后的当前上下文可能只有摘要和最近消息，而会话文件仍保存多倍于窗口大小的原始历史。

已用现有恢复代码做本地验证：压缩后的有效上下文包含摘要，不包含旧原文；历史快照仍包含旧原文；当前提议提示词还会因 4000 字符裁剪而丢掉旧消息尾部的证据。

因此：

- “提议切片”默认分析所选分支历史，不偷偷降级成只分析当前有效上下文。
- 可以提供明确的“仅分析当前有效上下文”范围选项，但结果必须标注该范围，不称为完整历史扫描。
- “起草要求”固定一个截止点，只分析其当时有效上下文及原回复，不需要重新发送整个后续历史。
- “找证据”允许分析用户选定的多个会话；分析窗口可以按会话分别构造，跨会话关系在导航和候选精查阶段处理。
- 读取本地记录不等于把记录一次全部发给模型。读取/index 和模型请求预算必须解耦。

### 2.1 来源读取与会话语义

使用现有 `buildSessionContext` / `contextAt` 的宿主恢复语义，不自行发明 compaction、reset 和 context_edit 的解释。

历史档案建立稳定索引：会话键、entry ID、分支顺序、角色、内容块、工具调用关联、压缩/reset 边界、摘要来源、原始内容摘要。读取有文件的长历史时采用流式索引和按需读取，避免整条原文在内存中反复复制；只有内存快照时使用宿主提供的记录，并明确本地资源限制。

本地读取上限是资源保护，不是模型上下文预算。触发资源限制时明确失败或标注未读取范围，不能输出完整扫描结论。

保留以下材料供分析：

- 用户与助手的可见文字。
- 工具名称、录制参数与工具结果，保留调用关联和错误标记。
- 已录制的 system/developer 指令及其生效位置。
- 宿主压缩摘要、上下文编辑和 reset 的记录及来源性质。

历史指令作为带角色、时间和出处的分析材料，而不是让辅助模型执行的指令。找不到历史系统提示时标为 missing，不能拿现在的系统提示补成“当时的要求”。宿主未录制的 hook 改写或供应商转换仍标为恢复局限。

不默认发送隐藏思考或私有签名。图片等材料按目标模型能力处理；无法分析的媒体要列入未支持材料，不能用文字省略标记冒充已读图片。

## 3. 模型预算：按实际请求计算

### 3.1 模型身份与限制

在调用开始时固定辅助模型和思考等级，读取宿主模型元数据：`contextWindow`、输出上限、支持的输入类型，以及可获得的独立输入限制。模型家族名、角色名、展示名都不能作为窗口依据。

若模型配置是动态路由，必须取得实际目标或可靠的路由上限；取得不到时展示限制未知，不按某个大窗口模型进行承诺。

注册表限制可能与网关、账户或自定义部署不同。允许一个可选的手动窗口覆盖值，并展示来源；覆盖值不能自动突破宿主或已知供应商的硬限制。没有可靠窗口信息时要求选择有元数据的模型或明确设置限制，不静默假设 128k。

### 3.2 预算关系

设：

- `C`：目标请求的有效总窗口。
- `I`：供应商独立输入上限，没有时使用 `C`。
- `R`：按供应商/宿主适配规则计算的生成预留，包含该接口计入窗口的思考和可见输出。
- `S`：协议开销、计数误差和安全余量。

则最终请求的可用输入预算为：

`B = min(I, C - R) - S`

完整请求的输入计数必须包含分析提示、历史材料、编号、出处、导航摘要、JSON 返回格式等；不是只数原始会话正文。若完整请求输入不超过 `B`，才进入直接发送路径。

思考强度通常不改变模型声明的总窗口，但可能改变生成预留和有效可用输入。不同接口对 reasoning/output 的计数方式不同，不能统一“再扣一个 thinking 值”，也不能统一认为 low 必然增加可用输入。

输出预留必须满足配置上限和目标模型限制。若输出预留本身使预算不可用，提示调整设置，不靠裁剪材料掩盖配置冲突。

### 3.3 Token 计数的可信度

优先使用宿主或供应商可获得的请求计数能力；其次使用匹配模型的本地 tokenizer。只有计数覆盖实际协议输入时才标为精确，否则标为估计并留更大余量。

没有匹配 tokenizer 时使用明确标为 heuristic 的保守估计，并显示依据。不能把“字符数除以 4”包装成精确 token 数，尤其不能对中文、代码和 JSON 使用无差别换算。

计数针对脱敏后、即将提交 SDK 的最终请求。供应商未暴露的转换开销计入余量和局限。最后一次预算检查仍然不能绝对保证未知网关不拒绝请求。

若服务方拒绝上下文长度，记录计划值、计数可信度和错误，停止该请求流程。遵循现有不自动重试、不自动换模型的策略；用户可以查看调整后的计划再重新发起。

## 4. 同模型与不同模型如何走同一套规划

| 条件 | 选择 |
| --- | --- |
| 历史原文与分析提示能装下 | 直接完整发送所选历史范围，无摘要替换 |
| 当前有效上下文能装下，但完整历史不能装下 | 历史扫描仍走多窗口；当前有效上下文可作为近期问题概览，不能替代早期原文扫描 |
| 辅助模型比会话模型窗口小 | 按辅助模型预算构造窗口；不把会话模型能装下当作辅助模型也能装下 |
| 换了模型，但窗口更大且历史能装下 | 同样走直接路径，不因为“跨模型”就强制摘要 |
| 单个候选的必要证据集合仍装不下 | 上下文不足；建议换大窗口模型、明确缩小分析范围或人工处理 |

同一个模型、仅思考等级不同、没有大量归档历史时，直接处理应当是常见路径。但还要检查分析提示新增开销、原回复、输出预留和上下文使用率；原会话已经贴近窗口上限时也可能需要多窗口。

这里“复用当前有效上下文”是复用宿主恢复的消息材料，不是复用当前 Agent 的执行状态、工具权限或隐式记忆，也不向当前会话追加分析消息。

## 5. 超预算历史：全覆盖扫描 + 原文精查

### 5.1 窗口边界

先按结构划分候选分析单元：一轮用户要求、助手回复、相关工具调用与结果；优先在完整对话轮、任务转向、压缩/reset 边界处分窗。

长度仍用于决定能否装下，但不用于删除内容。每个可分析原文片段都分配给至少一个主扫描窗口；重叠片段是额外上下文，不抵消其他片段的覆盖义务。

每条待评估助手回复指定一个主扫描窗口，防止依靠重叠消息反复产生同一道题。窗口开头附带必要的历史指令、会话阶段概览和来源索引，不能假装每个窗口都是从空白开始的新任务。

不使用“固定重叠 30 条就一定足够”的规则。跨窗口依赖由来源关联与候选的证据需求决定。

### 5.2 单条超长消息

单条消息也可能超过小模型预算，不能坚持“消息必须整体发送”，也不能只留头尾。

处理规则：

1. 按内容结构拆成可溯源片段：日志按记录/行，代码按结构或行，结构化结果按字段/数组项；结构无法解析时在安全字符边界拆片。
2. 保存父 entry ID、块编号、原文区间和内容摘要；所有片段最终都有明确处理状态。
3. 片段保留必要的容器信息、字段路径或相邻边界，不让 JSON 子片段被误认成完整对象。
4. 各片段扫描结果返回候选线索和所需引用，不直接宣称看懂了整条消息。
5. 需要联合比较多个片段时，精查阶段取回这些片段的原文。若联合证据仍超过预算，标为不足。

这是“分次读取完整材料”，不是“用截断文本代替完整材料”。它保证材料有机会被分析，不保证小模型能恢复所有跨片段语义关系。

### 5.3 扫描输出与导航摘要

窗口扫描返回：候选助手 entry、可能的依据 entry/片段、违反片段、相关问题线索、需要补充的上下文，以及带来源 ID 的短导航摘要。

导航摘要只用于找原文，不作为引文、事实证明、requirement 或 rubric 的直接依据。宿主原有压缩摘要也单独标为 host summary；它可能确实出现在当时被测上下文中，但不能因此冒充原始工具结果或用户原话。

长历史的窗口扫描可以同时产出摘要和候选，不额外引入一个“先智能推荐消息”的模型阶段。选择范围内的原文都要被分配扫描，避免推荐器提前漏掉关键材料。

跨窗口、跨会话关联使用来源索引和带 ID 的导航线索，再读取原文进行核对。有限索引和模型扫描不保证发现所有遥远关联；关系仍不明确时保留 unresolved，不称为“确认无问题”。

### 5.4 候选精查与补上下文

对候选构造最小充分证据包：

- 候选前的有效任务和指令。
- 完整的原出错回复，必要时拆片分析。
- 可能被违反的用户要求、工具结果或其他依据的原文。
- 理解这些依据必须的上下游消息和工具调用关系。

先完整尝试预算，不盲目只选“附近 N 条”。需要更早消息时，从索引定位并取回原文；可先使用宿主当时的有效上下文帮助定位，但不能把摘要当作原文替代。

辅助模型可以返回 `need_context` 和已知来源 ID/缺失事实描述。程序只在用户选定的来源范围内检索和读取，再提交新增证据；这是显式上下文补充，不是自动重试同一失败请求。

不增加 shell、写文件或通用 Agent 权限。引用的 ID、允许范围、读取量与额外调用上限由程序控制。无法定位来源、预算不足或用户不批准额外调用时，候选保持 incomplete。

## 6. 三重核验与时间隔离

每个最终引用必须同时通过：

1. **来源存在**：原始记录/稳定录制文本中确实存在该连续片段，来源内容摘要一致。
2. **辅助模型见过**：该片段确实包含在用于支持最终判断的分析请求中，而不只是存在于本地档案。前期只见过摘要的引用，必须先经过原文精查。
3. **被测模型当时可见**：依据出现在候选截止点前的有效上下文或可证明有效的历史指令中，而不是仅仅按时间早于截止点。

第三条尤其重要：压缩/reset 之前的原文可能存在于文件，却已经不在被测模型当时的输入中。继续使用 `requirementFromProposal` 按恢复输入重新定位的约束，不能因为历史扫描器看过它，就要求被测模型当时知道它。

脱敏后的发送片段也要有来源映射。不能只在完整本地原文上做 `includes` 就接受引文，更不能接受未发送的尾部内容。跨越脱敏替换段的引文不能自动恢复成模型提供的原文证据；要求改引用可核验片段或进入人工处理。

发现阶段允许查看后续纠正来定位问题，但不直接从全历史生成最终 rubric。候选形成后，起草阶段重新构造“截止点前有效上下文 + 原出错回复”，不发送后续纠正或最终根因。

这意味着：历史能装下一次请求时，候选发现无需分段；但产生最终要求仍有独立的时间隔离精查/起草步骤。增加的调用有明确目的和数量预告，不把“直接发送”承诺成整个流程永远只有一次调用。

## 7. 执行计划、UI 与 Debug

### 7.1 发请求前展示计划

在现有外发确认中增加：

- 选定会话、分支、分析范围，以及是否包含归档历史。
- 辅助模型与窗口来源、实际思考等级。
- 输入预算、输出预留、安全余量和计数可信度。
- 直接发送或多窗口的选择原因。
- 初始扫描请求数量，以及候选精查/补上下文可能增加的调用上限。
- 不支持或缺失的材料、脱敏命中。

默认不自动切换更贵的大窗口模型，不无限补上下文。初始计划与额外调用上限得到批准后执行；超过批准范围时再次确认。各阶段沿用宿主模型调用和既有用量记录，不引入子 Agent。

### 7.2 结果不再只有 accepted/rejected

执行结果区分：

| 状态 | 含义 |
| --- | --- |
| completed | 所选范围的所有计划请求成功返回，必要来源核验完成；不表示模型必然找出了所有错误 |
| partial | 有未发送、未支持、未完成或上下文不足的范围/候选 |
| failed | 读取、认证、模型调用或协议处理失败，无法完成计划 |
| cancelled | 用户取消，显示已发送与未发送范围 |

候选结果单独区分 `proposed`、`rejected`、`needs_context` 和 `no_candidate_returned`。空结果附模型的简短说明和相关来源 ID，但明确标为模型自述，不当作真实原因或“没有错误”的证明。

可以显示“发送了多少条待评估回复、多少原文片段”，不能声称知道模型实际注意到了每一段。摘要覆盖范围与原文发送范围分开统计。部分请求失败后，不能再通知为完整的“0 条通过、0 条丢弃，完成”。

### 7.3 Debug 的内容

在现有 Debug 菜单增加上下文计划和发送清单，保留请求、原始回复、解析与核对结果面板：

- 为什么选择这个窗口；包含哪些 entry/片段；哪些仅以摘要表示。
- 预算与最终请求估计，实际用量及停止原因。
- 引用在原始档案、分析请求和截止点有效上下文中的核验结果。
- 未发送范围、缺失来源、未支持媒体和停止原因。

默认只在当前调用中保存计划和诊断，不把会话正文、摘要或模型回复写入日志。需要复现时显示来源内容摘要和提示词版本；原会话文件变化后，不使用旧映射冒充当前来源。

## 8. 代码改动边界

| 文件/模块 | 改动 |
| --- | --- |
| `src/pi/read-session.ts`、`sources.ts` | 分离分析历史索引与有效上下文视图；保留历史指令和来源；长文件按需读取 |
| 新 `src/core/context-plan.ts` | 纯本地预算与窗口规划、原文片段覆盖、发送清单；不调用模型、不读取凭据 |
| `src/core/assist.ts` | 删除 `perEntryLimit` 和固定字符分块策略；渲染规划后的材料；区分导航摘要与原文引用；扩展候选/补上下文回复格式 |
| `src/pi/assist-run.ts` | 按计划执行扫描、精查和起草，管理批准范围与 incomplete/failed 状态，展示覆盖诊断 |
| `src/pi/model.ts` | 保留真实模型限制、计数可信度和可获得的完整用量；仍通过宿主 SDK 调用，不默认执行工具 |
| `src/pi/slice.ts` | 固定截止点起草只使用当时有效上下文；必要证据超预算时返回明确不足状态 |
| `src/pi/plugin-settings.ts`、`config-ui.ts` | 仅在元数据缺失/网关限制不同等场景提供可选窗口覆盖，保留现有 Debug 开关 |

`ContextPlan` 是内部执行数据：scope、来源内容摘要、预算来源、请求步骤、分配的原文片段和覆盖状态。无需建立通用 Agent 框架、向量数据库或新的评测协议。

保持主案例、案例格式和 Detroit 导出契约不变。分析补充信息不自动进入被测输入或评分。清理旧截断路径，避免新旧两种上下文策略并存。

## 9. 验收标准

1. 关键反证位于长消息第 4000 字符之后：它仍被分配并发送，引用能回到完整来源，不能只在未发送的原文里通过核验。
2. 同模型且所选历史能装下：一次候选扫描发送完整材料，不生成替代摘要；计数包含分析提示和输出预留。
3. 同模型但会话多次压缩：早期错误仍有历史扫描窗口；不能拿当前摘要范围冒充完整历史范围。
4. 小窗口辅助模型：所有请求按其预算规划；必要材料跨窗口时通过原文补上下文，无法容纳时显式 needs_context。
5. system/developer 要求在候选处有效：能定位和引用；后来出现或 reset 后不再有效的指令不能追溯评分。
6. 超长工具结果拆片：片段区间并集覆盖全部可分析内容，工具调用关联和字段路径不丢；跨片段判断有联合证据或显式不足状态。
7. 摘要引用、未发送片段、伪造 ID、脱敏替换段引文：不能直接确认成评分依据。
8. 只在后来纠正中出现的根因：发现阶段可以定位，但时间隔离起草不会收到该根因，评分不得要求当时猜中它。
9. 请求失败、长度拒绝、未知窗口、媒体不支持、取消：结果状态与未处理范围准确，不再显示误导性的“完整扫描无候选”。
10. Debug 与关闭状态得到相同的候选核对结果；无隐藏模型切换、无无限额外调用、无诊断正文落盘。

验证同时包括预算/区间/时间关系的确定性回归，以及实际宿主中的同模型直送、小窗口多请求和失败交互。真实模型不保证每次发现相同数量的候选；不把模型必然答出某个候选作为确定性单测。

## 10. 代价与限制

- 全历史能装下时不做预摘要，减少一次提前漏判的机会，但完整扫描成本可能高于只看最近窗口。
- 小窗口多请求会增加费用和时延；主窗口与必要上下文有重复发送，必须在确认界面说明。
- 原文全覆盖不等于语义关系全覆盖。小模型仍可能无法联合理解跨度很大的材料；明确不足比把摘要当证据更可靠。
- 历史恢复依赖宿主保存的记录。未录制的临时系统提示、工具 schema 变化和供应商改写不能凭当前状态补造。
- 保守估计和余量不能消除所有供应商拒绝；失败后不自动换模型或偷偷裁剪。

结论：默认完整发送能够装下的所选范围；超过预算才采用有出处、可追溯、可补原文的多窗口处理。核心目标不是“把会话压得足够短”，而是“在目标模型预算内构造足以支持具体判断的上下文，并诚实报告未能完成的部分”。
