# 长程任务的案例切片

> 版本 2026-10-13。状态：已实现阶段 A（人工版）和阶段 B（模型辅助），待用真实案例验收。实现位置见 §15。
> 来源：[讨论稿](long-trajectory-case-slicing-discussion.md)。本文取代讨论稿中的建议部分；讨论稿保留问题背景和那次只读 smoke 的记录。
> 和 [技术设计](casepick-technical-design.md) 的关系：本文扩展技术设计的第 3、7、8 节；起草模型的配置和外发规则以技术设计第 8 节③、第 10 节为准。

## 1. 要解决什么

真实的排障任务会跨多轮、甚至跨多个会话。助手在中途反复下错结论，最终的根因可能来自用户事后的复述。现在的 CasePick 只能"选一条出错回复，引用它之前的用户原话"，处理不了三种情况：

1. **没有明确要求的犯错**：用户没说过"不要无依据断言"，但助手在反证面前仍然坚持错误结论。
2. **同一个问题的证据散落在多个会话里**，单看一个会话说不清。
3. **事后才知道的事实**（比如最终根因）容易被误用为模型当时就该知道的信息。

## 2. 结论先行

| 做 | 不做 |
| --- | --- |
| 把长程任务里排障**过程**的犯错切成一道道 `next_message` 题 | 不做"找出根因"的题：需要代码、依赖和可运行环境，CasePick 拿不到 |
| 用"主案例"在内部把跨会话的证据串成时间线 | 主案例和证据不导出，对外只有普通案例 |
| 期望可以来自用户原话、截止点之前的事实、或一份固定的工作规范 | 不接受只有事后才知道的期望 |
| 模型提出候选切片，程序核对，人确认 | 不让模型改写原文、不让模型宣布根因已验证 |
| 每道题的输入来自原会话的一条分支（历史重放） | 第一版不做"重新编题"，不把汇编材料拼成输入 |

所以：**对外格式不变**，每个切片就是一条普通的 `detroit.case/v2`；变化集中在 CasePick 内部的来源读取、期望依据和 lint。

## 3. 概念

| 概念 | 是什么 | 存在哪里 |
| --- | --- | --- |
| 主案例（Issue） | 一个待解决的问题，可以跨多个会话 | 内部，`issues.jsonl` |
| 证据（Evidence） | 一段带出处的原文：哪个会话、哪个 entry、谁说的、什么性质 | 内部，挂在主案例上 |
| 切片（Slice） | 一道可以独立评测的题，有自己的截止点、输入和评分 | 就是一条案例，导出为 `detroit.case/v2` |

一个会话可以有多个主案例，一个主案例可以切出多道题。会话、主案例、单条回复互不等价。

```ts
interface Issue {
  id: string;                       // issue_<ulid>
  title: string;
  status: "open" | "resolved";
  evidence: Evidence[];             // 按原始时间排序
  resolution?: {                    // 最终结论，只进评审侧
    statement: string;
    evidence: string;               // 出处证据 ID
    confidence: "user_reported" | "reproduced";
    unknowns: string[];             // 材料里没有的细节，如"具体是哪个库、哪个调用点"
  };
  slices: string[];                 // 案例 ID
}

interface Evidence {
  id: string;
  session: string;                  // 会话 ID 的哈希
  entry: string;                    // 原会话 entry ID
  role: "user" | "assistant" | "tool";
  kind: "tool_output" | "user_statement" | "assistant_claim" | "user_correction" | "postmortem";
  at: string;                       // 原始时间，不是导入时间
  excerpt: string;                  // 原文片段，逐字
  content_hash: string;             // 整条原消息的摘要
  availability: "original" | "excerpt_only";
}
```

刻意不做的：证据之间"支持、反驳、修正"的关系图。第一版唯一需要的关系是"某个切片被哪条证据推翻"，记在切片上（§7）。

`resolution.confidence` 必须区分"用户口述的单步调试结果"和"独立复现过"，前者不能写成后者。

## 4. 来源读取

| 来源 | 怎么读 | 能不能当截止点、进输入 |
| --- | --- | --- |
| 当前会话的当前分支 | 现有做法（`getBranch()` 加 `buildSessionContext`） | 能 |
| 用户选定的其他会话 | 用户在界面里选会话文件后，只读打开，按 entry 父链取那条分支 | 能，切片的输入来自那个会话 |
| 汇编会话里的 `custom_message` | 带 `sourceSessionId` / `sourceEntryId` 时，回到原会话找对应 entry | 不能。只用来导航和建立时间线 |
| 原会话文件已经不在 | 只保留摘录 | 不能。证据标为 `excerpt_only`，只能进时间线和评审侧 |

规则：

- **一道题的输入只来自一个会话的一条分支。** 跨会话的材料不拼进输入，因为模型当时从来没有同时看到过它们。
- **读其他会话需要用户逐个选定**，选定范围记录在主案例上。不扫描整个会话目录。
- **只读。** 不执行会话里出现的命令，不把历史里的指令当成当前指令。
- **时间用原始时间。** 证据时间线按原会话 entry 的时间排序，导入时间单独记录。

## 5. 期望从哪里来

每条要求标明依据（`basis`），三种依据的出处都必须在截止点之前：

| `basis` | 期望从哪来 | `source` 指向 | 例子 |
| --- | --- | --- | --- |
| `instruction` | 用户或系统明确提的要求（现有做法） | 那句要求的原话 | "只输出 JSON" |
| `evidence` | 截止点之前已经出现、和出错回复相矛盾的事实 | 那条工具输出或用户陈述的原文 | 工具输出显示两端都是 ENABLE/0，回复却断言两端数据不同 |
| `norm` | 规范表里的一条通用工作规范 | 让这条规范生效的证据原文，另记规范编号 | 判定日志里的字段都一致但结果不同，回复却没有提出任何能区分假设的检查 |

### 5.1 规范表 `casepick.norms/1`

规范表随 CasePick 发布，有版本号，不能临时编造。第一版只放能直接观察判定的四条：

| 编号 | 规范 | 什么时候生效 | rubric 判什么 |
| --- | --- | --- | --- |
| N1 | 证据不足时不把单一原因说成确定结论 | 截止点之前的证据不能排除其他原因 | 回复是否用确定语气断言了某个原因，且没有说明还需要什么证据 |
| N2 | 出现反证时撤回或修正之前的假设 | 截止点之前出现了和之前假设直接矛盾的事实 | 回复是否仍然坚持被反证的假设，且没有回应反证 |
| N3 | 多个解释并存时，提出能区分它们的检查 | 现有证据同时符合两个以上的解释 | 回复是否给出了至少一个能让不同解释产生不同结果的检查 |
| N4 | 没做过的验证不说成已验证 | 截止点之前没有对应的工具输出或用户确认 | 回复是否声称"已确认、已验证"某件事，而截止点之前找不到依据 |

每条规范配一份默认 rubric 模板，模板里的判定问题只引用截止点之前的证据。增加规范要升规范表的版本，已导出的案例记录它用的版本。

### 5.2 防后见之明

1. **要求和 rubric 只能依据截止点之前的引文和规范表。**
2. **截止点之后的任何内容只能进 `diagnostic`**：原出错回复、用户纠正、后续会话、最终根因，都一样。
3. **lint 做确定性检查**：rubric 和要求文字里，如果有一段连续文字（默认 12 个字符；以中日韩文字为主时 8 个字）**只**出现在截止点之后的内容里（包括同一会话里截止点之后的全部消息、同一主案例的后续证据和 `resolution`），而不出现在截止点之前的输入里，就阻止确认。也在截止点之前出现过的片段不算，所以重复引用原要求不会误报。
4. **不能要求模型猜中当时无从知道的东西。** 早期切片可以要求"不要在已有反证时断言旧版本"，不能要求"指出是类型转换库的问题"。

## 6. 切片规则

**一个位置能成为切片，必须同时满足：**

- 截止点是原会话里一条真实的 assistant 消息；
- 截止点之前有可以逐字引用的依据（§5 的三种之一）；
- 这条回复违反了依据，并且能从回复原文里截出 `origin: observed` 的违反片段。

**不切的情况：**

| 情况 | 原因 |
| --- | --- |
| 工具或环境报错导致的失败 | 偏向环境问题，不是推理失败 |
| 用户后来改了目标或加了新需求 | 不是此前犯错 |
| 截止点之前的证据不足以判断 | 模型当时无从知道 |
| 只有事后才知道错在哪 | 违反防后见之明规则 |

**去重**：同一个主案例里，"依据编号（规范编号或 `instruction`）+ 推翻它的证据"相同的切片只保留最早的一个。助手后面重复同一个错误，不再出题。

**分组**：切片的 `provenance.source.group_key` 用主案例 ID，不用会话 ID。导出验证集时，同一个主案例只要有切片已经进过改进集，就提示冲突。

## 7. 对外格式

每个切片导出为一条普通的 `detroit.case/v2`（技术设计第 7 节），和单条回复的案例完全一样。新增的信息放在 `extensions["x-casepick"]` 里：

```jsonc
"extensions": {
  "x-casepick": {
    "cutoff_entry": "a1b2c3",
    "issue_id": "issue_01JC…",
    "requirements": {
      "r1": { "basis": "evidence", "refuted_by": ["ev_07"] },
      "r2": { "basis": "norm", "norm": "N2", "norms_version": 1 }
    }
  }
}
```

- `diagnostic.notes` 可以写上后来确认的根因，必须注明来源和 `confidence`，比如"用户事后口述的单步调试结果，未独立复现"。`diagnostic` 本来就不进被测输入，也不是 rubric 的依据。
- `group_key` 用主案例 ID。
- 主案例、证据时间线、`resolution` 都不导出。
- **向 Detroit 申请的扩展**：在 requirement 上加一个可选的 `basis` 字段（`instruction` / `evidence` / `norm`），作为协议的小版本升级。Detroit 支持之前，信息只在 `x-casepick` 里。

## 8. 模型辅助

模型配置、外发确认、脱敏都按技术设计第 8 节③和第 10 节：默认用当前会话的模型、思考等级 low，可以在 `/casepick config` 里改。

模型做三件事，每件都只返回 ID 和理由，由程序核对后再给人看：

| 任务 | 模型返回 | 程序核对 |
| --- | --- | --- |
| 标注证据性质 | 每个 entry 的 `kind` | entry ID 存在，属于已选定的会话 |
| 提出候选切片 | 截止点 entry ID、依据类型、规范编号、引文、违反片段、rubric 草稿 | 截止点是 assistant 消息；引文逐字出现在截止点之前；违反片段逐字出现在截止点；规范编号在规范表里；通过防后见之明检查 |
| 提出主案例归并 | 哪些证据属于同一个问题，附理由 | 证据 ID 存在 |

规则：

- 模型的输入按需截取：只发用户选定的会话里、和主案例相关的 entry，并给每条编号。长会话分段发送，**分段摘要只用于导航，不能当证据**。
- 核对不过的字段清空、标为需要人工补，不让模型重试。
- 模型不改写原文，不决定 `resolution.confidence`，不确认切片。
- 不配置模型时，以上三件事都可以人工完成。

## 9. 审阅界面（TUI）

在 `/casepick` 主菜单里加一个入口"整理长程问题"：

1. **建主案例**：输入标题，选定要读的会话（默认只有当前会话，可以从会话列表里添加）。
2. **看时间线**：按原始时间列出证据，每条显示会话、角色、性质和摘录。可以人工标性质，也可以选"用模型标注"。
3. **找切片**：人工选一条 assistant 回复作为截止点，或者选"用模型提议"。每个候选显示依据、引文、违反片段和 rubric 草稿。
4. **审阅切片**：和现在的单条案例审阅一样，增加依据类型、规范编号的编辑，lint 结果里多出防后见之明检查。
5. **记录结论**（可选）：填写 `resolution` 和缺失的细节。

主案例可以拆分和合并；切片可以换截止点，换了之后依据和引文重新核对。

## 10. 新增的 lint

| 检查 | 不通过时 |
| --- | --- |
| `basis` 是 `evidence` / `norm` 时，引文所在的消息在截止点之前 | 阻止确认 |
| 规范编号在当前规范表里 | 阻止确认 |
| rubric 和要求文字里有只出现在截止点之后的长片段（§5.2 第 3 条） | 阻止确认 |
| 切片的输入只来自一个会话的一条分支 | 阻止确认 |
| 证据 `availability` 为 `excerpt_only` 的条目被用作截止点或输入 | 阻止确认 |
| 和同一主案例已确认的切片"依据 + 推翻证据"相同 | 警告：疑似重复 |

## 11. 例子：书号 7658094881453132862

材料见讨论稿第 2 节。按本文的规则，一个主案例，三个候选切片：

| 切片 | 依据 | 出处（必须在截止点之前） | 违反的是什么 |
| --- | --- | --- | --- |
| 原始字段一致，仍断言置顶数据不同 | `evidence` + N1 | 两端置顶状态都是 ENABLE/0 的输出 | 用确定语气断言两端数据不同 |
| 用户确认已全量，仍断言旧版本 / 旧构建 | `evidence` + N2 | 用户说生产实例和 `cac32df…` 对齐、新代码已全量 | 没有回应反证，仍坚持旧版本假设 |
| 判定条件看似一致，输出却不同 | `norm` N3 | 判定日志里 `originAppLevel`、`updateStop`、`changduProfileScore`、`setTop` 一致，但 `hasHide=-1` | 没有提出能区分"数据不同"和"转换不同"的检查 |

- 三道题都不要求模型说出"类型转换库"。
- "两边使用的类型转换库不同"只进 `resolution`，`confidence: "user_reported"`；具体的库名、调用点、枚举类型、修复提交都列入 `unknowns`。
- 这些还不是确认过的题。每道题都要回到原会话找到准确的截止点，确认截止点之前确实有上述证据。

## 12. 分期与验收

**阶段 A：人工版**

- 主案例、证据时间线、读取用户选定的其他会话、`custom_message` 回溯到原会话。
- 三种依据和规范表 v1，切片审阅，新增 lint，导出时用主案例 ID 作为 `group_key`。
- 验收：用 §11 的真实材料建一个主案例，三个来源会话都能进时间线；至少一道切片能确认导出；`resolution` 不出现在任何导出文件的 `task` 和 `scoring` 里；原会话文件没有被修改。

**阶段 B：模型辅助**

- §8 的三项任务，核对规则，用量记录。
- 验收：模型提出的引文和截止点 ID 全部经过核对；伪造的 ID 和引文被清空；用户可以逐条拒绝；记录候选被接受的比例。

**暂不规划**：重新编题、多步评测（`episode`）、根因发现题。前提是 Detroit 支持多步执行，并且确实有能恢复环境的案例。

## 13. 指标

- 候选切片被接受、修改、拒绝的比例，分人工和模型两类统计。
- 防后见之明检查的拦截次数，以及被拦下后用户怎么处理。
- 疑似重复警告的次数。
- 主案例被拆分、合并的次数，用来估计归并出错的程度。
- 每个主案例平均产出几道确认的题。

## 14. 待确认

| 问题 | 本文方案 | 另一种选择 |
| --- | --- | --- |
| 规范表第一版的条目 | N1–N4 四条 | 先只做 N1、N2，等真实数据再加 |
| 防后见之明检查的阈值 | 12 个字符，中日韩文字为主时 8 个字；只在截止点之后出现才算 | 更长的阈值以减少误报 |
| 读取其他会话的范围 | 用户逐个选会话文件 | 允许按项目目录批量选择 |

## 15. 实现位置

| 模块 | 内容 |
| --- | --- |
| `src/core/issues.ts` | 主案例、证据、时间线、切片去重、截止点之后的内容、合并和拆分 |
| `src/core/norms.ts` | 规范表 `casepick.norms/1` 和默认 rubric 模板 |
| `src/core/assist.ts` | 找证据、提议切片的提示词，回复解析和逐条核对，提议转成要求 |
| `src/core/lint.ts` | 防后见之明检查（`rubric_hindsight`）和依据检查（`basis_*`、`norms_version_unknown`） |
| `src/schema/case.ts` | `x-casepick.issue_id`、`x-casepick.requirements` |
| `src/store/issues.ts` | `issues.jsonl`：按修订追加，另一个窗口改过时拒绝覆盖 |
| `src/pi/sources.ts` | 只读解析其他会话文件（不经过 `SessionManager.open`）、取主分支、汇编消息回溯 |
| `src/pi/slice.ts` | 从任意会话的截止点生成切片草稿 |
| `src/pi/assist-run.ts` | 模型辅助的执行流程：外发确认、逐个请求、核对 |
| `src/pi/issues-ui.ts` | `/casepick` → "整理长程问题" 的界面 |

实现时和本文前面的设计相比，有两处取舍：

- **其他会话只读主分支**：文件里最后一条带 ID 的条目沿父链回溯到根。已放弃的分支不读，和当前会话的处理方式一致。
- **重复切片的判定键**用"依据类型 + 规范编号 + 出处引文原文"，而不是证据 ID，因为切片的出处在重建后的输入里，和时间线证据不一定一一对应；能对上的证据 ID 记在 `refuted_by` 里。
