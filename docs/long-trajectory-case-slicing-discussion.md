# 讨论稿：长程任务的案例归并与评测切片

状态：已有结论，见 [长程任务的案例切片](long-trajectory-slicing.md)。本文保留为问题背景和讨论记录；以下建议部分以新文档为准。

原状态：供与 Opus 讨论的需求与设计建议，尚未批准实施。本文不代表功能已经实现，也不授权执行历史会话中的命令、修改或发布建议。

## 1. 要解决的问题

CasePick 当前以“选择一条 assistant 错误回复”为提取入口。但真实工程任务可能经过多轮调查、用户纠正、跨会话继续，最终根因甚至来自用户事后的调试复述。

需要讨论的能力是：从长程轨迹中识别问题，归并同一问题的证据，再形成可独立评测的切片，而不是机械地按消息数量切分，或把每次错误回答当作无关案例。

三个概念必须分开：

- **主案例 Case**：一个待解决的问题，可以跨多个 session。
- **证据 Evidence**：原文、出处、时间、角色及证据性质。
- **评测切片 Slice**：一次具体评测的输入截止点、观察窗口和评分依据。

一个 session 可以包含多个主案例；一个主案例可以产生多个切片。Session、case、单条回复不等价。

## 4. 插件形态是否适合

建议：**适合做案例生产入口，不承担完整评测运行。**

Harness 靠近原始现场，方便读取分支、消息 ID、工具结果、压缩记录和用户标记。但会话不等于当时真正发给模型的完整请求，更不等于文件系统、数据库或远端环境。

继续保持分工：CasePick 整理与导出；Detroit 或环境提供方负责执行评测。

现有 `docs/casepick-technical-design.md` 明确限定主动触发、next_message、不恢复运行环境。长程切片是产品范围扩展，需要显式讨论，不能视为原设计已包含的功能。

## 5. 建议设计

### 5.1 来源读取与证据记录

- 区分原生消息、历史引用和后来的复盘。
- 对已有来源字段的导入材料建立原始记录关联；在用户批准的来源范围内读取、校验。
- 原文件不可用时保留摘录，标记上下文不完整。
- 原始时间与导入时间分开记录；跨会话不能仅按时间戳拼成模型当时看过的上下文。
- 保存原始 session/entry ID、片段定位、角色、内容哈希及来源状态。
- 区分工具观测、用户报告、助手假设、后续纠正；支持“支持、反驳、修正”关系。
- “用户报告单步调试确认”与“独立复现成功”必须分开。
- 不执行引用中的命令，不把历史指令升级为当前指令。

### 5.2 案例编辑核心

提供分析来源、合并/拆分主案例、调整切片、确认证据、校验导出的操作。来源核对、时间关系和引用完整性集中实现，避免 UI、模型起草和导出各自维护不同规则。

主案例与证据可作为内部编辑模型；对外继续采用 Detroit 协议。新增字段、跨会话 group_key 及多步窗口的映射需要与协议核对，不能假定下游已经支持。

### 5.3 模型辅助，不让模型替代证据

模型适合提出问题归并、切片位置和 rubric 草稿。模型输出引用 ID 和理由；程序核验 ID、原文与时间关系，并从来源确定性构建最终输入。

- 模型不直接改写历史原文，不直接宣布根因已验证。
- 无模型配置时仍支持人工整理。
- 外发前预览范围并取得同意；考虑日志中的个人信息和凭据。
- 起草模型不需要 shell、文件修改或发布权限。
- 分块摘要可用于导航，但最终证据必须回到原文，不能以摘要替代出处。

### 5.4 切片标准

每个切片必须明确：当时的任务、可见证据、观察窗口、可判定的成功标准。

候选位置可以是新证据推翻假设、用户纠正、工具结果与结论矛盾、调查转向确定归因或执行、目标变化。

不能把新需求误判为此前犯错，不能把工具错误自动归因为推理失败，也不能把同一种误判重复切成大量近似题。

### 5.5 作答视图与评审视图隔离

- **作答视图**：截止点当时可见的输入、工具和环境说明。
- **评审视图**：原失败输出、后续事实、最终根因、评分依据。

最终根因不得提前进入“发现根因”题目的 task.system 或 task.messages。

后验事实可以证明旧结论错误，但不能增加模型当时应当知道的信息。早期切片可以要求“不要无证据断言旧版本；提出有区分力的验证”，不能要求模型猜中尚无源码依据的具体转换库名称。

必须区分“后来的新要求”和“后来用于判定原任务正确性的事实”。当前只围绕显式要求违反的提取模型是否需要扩展，是本次讨论的重要点。

### 5.6 历史重放与重新编题

- 历史重放：尽量恢复原截止点上下文，保留分支、压缩语义，注明恢复局限。
- 重新编题：选择必要证据构成独立题目，明确标记为派生题，不声称是原模型当时输入。

两者都可以有价值，但不能混标。汇编材料适合派生编题，不天然等于历史重放。

## 6. 本案例可以形成哪些切片

保留一个主案例，按证据完整度考虑以下切片：

| 候选切片 | 评测目标 |
| --- | --- |
| 原始字段一致，仍断言置顶数据不同 | 区分原始数据与运行时转换结果，避免过早排除路径 |
| 用户确认版本及全量，仍断言旧版本/旧构建 | 根据反证撤回假设，不以猜测充当唯一解释 |
| 条件看似一致但输出不同 | 进一步检查实际类型、依赖和转换语义 |

这些不是已确认的评测题。仍需选择精确截止点，检查当时证据是否足够，编写公平 rubric。

完整根因发现能力还需要代码、依赖和可运行环境。材料缺失时可以保存案例资料，但不能把它标为可执行的完整排障评测。

同一主案例的切片不能分散到改进集与验证集；跨案例共享大量来源也需要泄漏检查，单靠 session ID 分组不够。

## 7. 建议的实施顺序与验收

1. **来源、主案例、人工切片**：能定位历史错误回复；三个来源归属一个主案例；根因只进入评审侧；缺失实现细节显式保留；原始会话不变。
2. **模型辅助归并与起草**：先审阅主案例和证据时间线，再审阅切片；支持合并、拆分、移动截止点；模型引用可核对，用户可拒绝。
3. **多步评测对接**：与 Detroit 对齐观察窗口、环境契约和评分方式；不支持或环境不完整时阻止误导性的可运行导出，不伪装成 next_message。

验证重点应是历史身份、时间隔离、后验信息泄漏、缺失来源、分支/压缩语义、评分公平性、跨切片数据集泄漏，而不只是 JSON schema 通过。

## 8. 希望与 Opus 讨论的问题

1. 主案例—证据—切片是否是合适的最小模型？哪些关系确有必要，哪些会过度设计？
2. 首先支持历史重放还是派生编题？两种模式如何避免混淆？
3. 如何处理原任务没有明确说“不要无依据断言”，但输出存在事实或推理错误的案例？
4. 如何区分后来的评分事实与后来新增的要求，避免 hindsight bias？
5. 自动归并与切分应保留多少人工确认？如何衡量错合并、错拆分和重复切片？
6. 现有 Detroit 协议能承载哪些信息？哪些应留在 CasePick 内部，哪些需要协商扩展？
7. 如何构建既不泄漏最终答案，又有足够证据支持根因发现的真实评测题？

推荐方向：保留插件形态，先成为有证据出处的案例编辑器，再增加自动归并与切片。不要先追求自动生成大量案例，而忽略题目边界、答案泄漏和评审公平性。
